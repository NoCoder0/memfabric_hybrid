昇腾 A3 与鲲鹏 CX7 RoCE 部署及离线排障指南

适用场景：昇腾 A3 卡侧 device_rdma 经以太网交换机访问鲲鹏服务器 CX7 网卡。以本实验室 16 个 NPU device 端口 × 16 个 CPU 网口 为例，覆盖地址和路由、双向连通性、RDMA READ/WRITE 带宽、两端及交换机 QoS 检查。

基线日期：2026 年 11 月 14 日，北京时间。本文依据会话中的配置回读、命令和实测日志整理。它是一份部署操作手册，不是本次重新登录环境的健康报告。客户现场替换 IP、接口、设备号和交换机端口后使用。

现场顺序：核对端口身份 → 物理链路 → 地址与源路由 → 双向 ping 和邻居 MAC → MTU → QoS → 单对 READ/WRITE → 拥塞和业务验证。 每一步通过再进入下一步。命令分为“查询”“主动测试”“配置变更”；配置变更段应在业务可中断时执行，并保留原值。

3 地址与源地址路由

3.1 为什么必须有源路由

一台 Host 的四个物理网口都在 /22，系统普通路由可能选择其中一个口发送。A3 同一卡的芯片也可能共享路由视图。因此，只改掩码、只指定目标 IP、或者看到 ping 回复，都不足以证明选定端口可用。

Host 按源 IP 和数据网段选择独立路由表；NPU 用 hccn_tool 添加源规则与指定 ethN 的直连路由。管理默认路由与 NPU 内部 192.* 路由保留。

3.2 Host3 H3-0 的只读检查

IF=enp165s0f0np0
SRC=20.168.0.19
DST=20.168.0.3

ip -4 addr show dev "$IF"
ip -4 rule show
ip -4 route show table 201
ip -4 route get "$DST" from "$SRC"
sysctl net.ipv4.conf.all.arp_ignore net.ipv4.conf.all.arp_announce net.ipv4.conf.all.rp_filter
sysctl "net.ipv4.conf.$IF.arp_ignore" "net.ipv4.conf.$IF.arp_announce" "net.ipv4.conf.$IF.rp_filter"

预期关键字段（行格式可能不同）：

inet 20.168.0.19/22
10201: from 20.168.0.19 to 20.168.0.0/22 lookup 201
20.168.0.0/22 dev enp165s0f0np0 ... src 20.168.0.19
20.168.0.3 from 20.168.0.19 dev enp165s0f0np0 table 201 ...
arp_ignore = 1
arp_announce = 2
rp_filter = 2

arp_ignore=1 限制在拥有目标地址的接口应答；arp_announce=2 控制 ARP 源地址选择；rp_filter=2 为宽松反向路径检查。检查 all 与接口配置的合成效果，不能只读接口值。这里选择 2 是本多口同子网方案的基线，不是所有网络都必须关闭反向路径检查。Linux IP sysctl 定义

4 如何验证 256 组双向全互联

本文“256 组”特指 16 NPU × 16 CPU，不包含 NPU↔NPU、CPU↔CPU。每组两个方向分别发起，共 512 次方向性测试。

4.1 先测一组并核对身份

A3 D：device 2 → Host3 H3-0。

timeout 16s /usr/local/Ascend/driver/tools/hccn_tool \
  -i 2 -ping -g address 20.168.0.19 pkt 64
/usr/local/Ascend/driver/tools/hccn_tool -i 2 -arp -g

Host3：H3-0 → device 2。

ping -n -c 3 -W 1 -w 5 \
  -I enp165s0f0np0 -I 20.168.0.19 20.168.0.3
ip -4 route get 20.168.0.3 from 20.168.0.19
ip neigh show to 20.168.0.3 dev enp165s0f0np0

两个 -I 是本环境 iputils 支持的接口绑定及源地址绑定写法。客户版本若不支持，先确认源策略路由正确，使用 -I 20.168.0.19，并通过路由、邻居和接口计数证明实际出口。

预期两端均显示 3 packets transmitted, 3 received 和零丢包。NPU pkt 64 是报文大小参数，不是发 64 个包；此版本默认发 3 个。Host 邻居 MAC 应为 device 2 的 c0:3e:50:1d:6b:4b；NPU 的 eth2 上 CPU 邻居应为 a0:88:c2:70:84:4e。

必须解析收发统计。hccn_tool 某些失败输出仍返回进程退出码 0；超时或缺少统计一律记为失败/未知。STALE 邻居可以是正常动态缓存状态；INCOMPLETE、FAILED 或错误 MAC 不能通过验收。

4.2 从所有 NPU 测到所有 CPU

主动测试，在 A3 D 的 bash 执行。 以下顺序执行 256 次，输出包含完整原始统计；保存到本次独立日志目录。

HCCN=/usr/local/Ascend/driver/tools/hccn_tool
CPU_IPS=(
  20.168.0.23 20.168.1.24 20.168.2.31 20.168.3.32
  20.168.0.21 20.168.1.22 20.168.2.29 20.168.3.30
  20.168.0.19 20.168.1.20 20.168.2.27 20.168.3.28
  20.168.0.17 20.168.1.18 20.168.2.25 20.168.3.26
)
LOGDIR="npu_ping_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$LOGDIR"
for d in $(seq 0 15); do
  $HCCN -i "$d" -ip -g > "$LOGDIR/dev${d}_ip.txt" 2>&1
  $HCCN -i "$d" -ip_rule -g > "$LOGDIR/dev${d}_rules.txt" 2>&1
  $HCCN -i "$d" -ip_route -g table "$((201+d))" > "$LOGDIR/dev${d}_route.txt" 2>&1
  for dst in "${CPU_IPS[@]}"; do
    timeout 16s "$HCCN" -i "$d" -ping -g address "$dst" pkt 64 \
      > "$LOGDIR/dev${d}_${dst}.txt" 2>&1
    rc=$?
    printf 'device=%s dst=%s exit=%s\n' "$d" "$dst" "$rc"
    cat "$LOGDIR/dev${d}_${dst}.txt"
    $HCCN -i "$d" -arp -g > "$LOGDIR/dev${d}_${dst}_arp.txt" 2>&1
  done
done

    ip -4 route get "$dst" from "$src" > "${prefix}_route.txt" 2>&1
    ping -n -c 3 -W 1 -w 5 -I "$nic" -I "$src" "$dst" > "${prefix}_ping.txt" 2>&1
    rc=$?
    printf 'source=%s interface=%s device=%s exit=%s\n' "$src" "$nic" "$d" "$rc"
    cat "${prefix}_ping.txt"
    ip neigh show to "$dst" dev "$nic" > "${prefix}_arp.txt" 2>&1
  done
done

每台应有 64 条 ping 统计，四台合计 256 条；与 A3 的 256 条组成双向记录。某次有丢包可以另存复测结果，但不能覆盖第一次失败证据。现场要保留时间、源/目的 IP、接口、收发包数、路由、两侧 MAC。

4.4 冷 ARP 验证

热邻居缓存可能掩盖广播 ARP 故障。此前 H1-1、H2-2 “只有一张 NPU 能通”就是典型案例：netdetect 或其他流量保留了个别 MAC 缓存。

以下操作删除指定目标的动态邻居，会触发重新学习；在维护测试期间执行，不要全局 flush，也不要删除业务要求的静态邻居。

# 随后执行 device2 -> H3-0 的 ping，再查 MAC

5.5 什么结果算通过

两端进程正常结束，报表的本地/远端 GID 分别对应选定 IP，显示 Mtu : 4096[B]、1 MiB 消息、有效迭代次数大于零。对比两端同一项平均带宽和迭代数，本环境应一致。

本场景空闲 200G 链路，单对 1 MiB 持续 READ/WRITE 基线约 196 Gbit/s，约 24.5 GB/s。这是同硬件和同参数的参考值，不是所有客户硬件的硬性验收门槛。持续时间模式可能打印 BW peak=0，应读取 BW average，不能判定为零吞吐。perftest 的客户端/服务端与参数语义参见上游说明。

同时比较测试前后的错误/重传/丢弃计数，以及 priority4 字节增量。没有拥塞时 PFC 帧计数可以不增加；单对跑满并不能证明拥塞时 PFC 有效。

hccn_tool -bandwidth -g time 1000 只观察已有流量，不会主动产生带宽测试。-roce_test 测的是工具缓冲区的 RDMA 能力；其缓冲区是否 HBM 尚未确认，不能据此声明 hcomm Host DRAM→NPU HBM 业务已通过，也不能替代 1600×656 B 的时延测试。

5.6 缩短验收时间

优先做 256 组双向小包连通性；带宽先做覆盖所有 NPU 和所有 Host 端口的配对，再抽跨历史网段及修复口。仅覆盖每端点一次至少需要 16 对；随机 10 对不可能覆盖全部 16 个 NPU。

现场 10 对、读写各 5 秒，含建链与采集约 4 分钟；早期 256 对串行读写全量耗时约 89 分钟。纯运行时间 256×2×5=2560 秒，约 42 分 40 秒，实际还要加建链/采集/切换，不能按 21 分钟估计读写两项。

需要测整体吞吐时可做多对并发，但必须控制共享双口 NIC、PCIe、NUMA 与 Host 内存带宽。并发总带宽不能证明所有组合都通，也不能用 16×196 当保证值。验证 PFC 时，应设计受控多对一拥塞场景，观察发送端实际降速、队列/PFC变化、停止负载后恢复及丢弃/重传，而不只是数总带宽。下面给出本场景已完成的两轮8路并发和四对一实测。

6.4 广播 ARP 异常与 pool 规避

buffer 号与 pool 号不是同一个概念。 priority→buffer 决定接收哪个缓冲；SBCM 决定该 buffer 关联的共享 pool。mlx5 接收方向通常把 pool0 用于 lossy、pool1 用于 lossless。正常的 lossy pool 在低流量下也应接收 ARP；“有损”不能解释本次所有广播都丢失。

本环境两个异常口曾出现：物理口广播计数增加40、vPort广播增加0；单播 ARP 10/10，广播 ARP 0/10。只把 buffer1 的 SBCM.pool 从0改1，广播恢复10/10；改回0再次失败。单独开启全局 PAUSE 未解决。由此确认了有效规避，但没有定位固件内部最终丢弃原因，不能写成已证实的通用固件缺陷。

本实验室实际修复命令，客户侧先核对 MAC、BDF、版本与同样的故障证据：

# Host1 H1-1，20.168.1.24
mlxreg -d 0000:26:00.0 --reg_name SBCM \
  --indexes local_port=1,dir=0,pg_buff=1 --set pool=1 --yes
# Host2 H2-2，20.168.2.29
mlxreg -d 0000:a5:00.1 --reg_name SBCM \
  --indexes local_port=1,dir=0,pg_buff=1 --set pool=1 --yes

回读将 --set pool=1 --yes 换为 --get，预期 pool | 0x00000001。两口当时仅变这个字段，PBMC/PAUSE/PFC保持原值。后续全量 QoS 调整时也保留了所有口 buffer1→pool1 的映射。

另六个口需要额外恢复 buffer1 阈值：H1-0、H2-1、H3-0、H3-1、H4-0、H4-1。 最终回读为 lossy_1=0,xon_threshold_1=963,xoff_threshold_1=1033，其余十个口 lossy_1=1 也通过冷 ARP。不要因为存在这项差异就一律修改。

# 仅适用于已复现该问题且验证过的端口与版本；BDF 从目标接口查询
mlxreg -d "$BDF" --reg_name PBMC --indexes local_port=1 \
  --set lossy_1=0,xon_threshold_1=963,xoff_threshold_1=1033 --yes

buffer1 的上述设置不代表开启 PFC0：PFCC 仍只允许 priority4，且全局 PAUSE 收发关闭。每项改动后都单独回读、冷 ARP、读写带宽、丢弃计数验证。复原 pool=0 在本故障口会重现中断，应仅在明确的回滚或对照实验中执行。网卡/驱动升级后应重新验证规避，不应无条件写低层寄存器。

9 持久化与变更后复查

9.1 Host

ip、ethtool、mlnx_qos、mlxreg 的一次运行不能自动保证重启/驱动重载后恢复。先确认现场网络管理器；本场景使用 NetworkManager。

cat /etc/sysctl.d/99-rdma-fullmesh-20261113.conf

本场景 /22、指定接口路由和源规则已保存在原 NM 连接中，接口 sysctl 保存在上述文件。客户应将第3节的运行态配置同步到所用管理器；避免直接重启整个 NetworkManager 或覆盖管理网连接。修改 MTU 持久化的例子：

# 配置变更，只保存所选连接的 MTU；不自动把地址/路由一并持久化
nmcli connection modify 'enp165s0f0np0' 802-3-ethernet.mtu 8192

对于只有本数据 IP、没有现存静态路由/规则冲突的连接，下列 NM 语法与本次部署脚本一致。连接名必须来自前面的查询；含多个 IP 或已有策略时需合并，不能用单地址覆盖。已存在正确路由/规则时，不重复使用 + 添加。

# 配置变更，Host3 H3-0 的持久化示例
CON=enp165s0f0np0
nmcli connection modify "$CON" \
  ipv4.addresses 20.168.0.19/22 \
  +ipv4.routes '20.168.0.0/22 table=201 src=20.168.0.19' \
  +ipv4.routing-rules 'priority 10201 from 20.168.0.19/32 to 20.168.0.0/22 table 201' \
  802-3-ethernet.mtu 8192
nmcli device reapply enp165s0f0np0
# 之后重新检查 ip addr、ip rule、table201、MTU 和管理路由

将每个数据接口的三个 sysctl 值写入本机专用配置文件，再只加载该文件。例如 H3-0 的文件内容为：

其它三个接口按各自名称追加。保存为客户自己的 /etc/sysctl.d/99-rdma-fullmesh.conf 后，执行 sysctl -p /etc/sysctl.d/99-rdma-fullmesh.conf 并回读；不要覆盖已有的同名运维文件。

HCCN=/usr/local/Ascend/driver/tools/hccn_tool

# 在这里进行同一项测试
$HCCN -i 2 -stat -g > npu_after.txt

查看各项 after-before，不要为了方便清空设备全部统计。计数回绕、驱动重载或重启导致 after<before 时，本窗口不可直接求差，应重新取基线。

计数或观察 判断用途
Host rx_prio4_bytes / tx_prio4_bytes READ时主数据TX增加，WRITE时主数据RX增加；对比其它priority，确认选对队列
Host rx_crc_errors_phy、rx_discards_phy、rx_out_of_buffer、priority buf_discard/discards 空闲单对正常基线期望无相关错误增量；按版本实际存在字段读取
Host rx_pause_ctrl_phy、tx_pause_ctrl_phy 与 prio4 pause相关字段 区分全局PAUSE与PFC，结合配置和实际拥塞解释
Host PHY广播与vPort广播 PHY收到而vPort没有，定位到网卡接收路径，不能直接归咎交换机
NPU roce_new_pkt_rty_num 及其他错误/重传项 增量说明传输重试，应继续定位丢包/拥塞/配置
交换机queue4、Discard、CRC、PFC 确认分类和逐跳传输；异常应沿数据方向逐口追踪

PHY、vPort、netdev等计数层次不同，不能把物理接收到包等同于Linux收到包；参见mlx5计数器定义。取不到字段应写“该版本未提供”，不能填0。

10.2 抓 ARP 时避免改变观察条件

# 目标Host口，-p表示不打开混杂模式
timeout 15s tcpdump -p -eni enp38s0f0np0 arp

# 另一个同VLAN正常Host上，用该工具支持的 -b 持续发送广播ARP
arping -b -c 10 -I enp38s0f0np0 -s 20.168.1.20 20.168.1.24

这是Host3 H3-1向Host1 H1-1的辅助诊断，不能替代NPU发起的测试。使用 -b 前核对所装arping帮助；部分版本默认收到回复后转为单播，可能掩盖广播问题。抓包为空时结合PHY/vPort计数及交换机出口证据；硬件卸载的RoCE数据不保证能被普通tcpdump看见。

10.3 按症状选择下一步

症状 首先检查 避免误判
管理IP全部超时 运维VPN/跳板/管理网 不能据此断定数据面断开
Link DOWN 两端光功率、LOS/LOL、FEC、模式、拆分子口、线缆 改IP/PFC不能解决光路问题
只同历史第三段IP能通 掩码仍/24？是否实际跨VLAN？ “交换机全互联”不自动改变主机路由
ping通但MAC属于别口 源规则、出口、ARP参数、实际GID 可能走了兄弟网口
只有个别NPU能通/热缓存通 定向清动态邻居，抓广播，查PHY/vPort与SBCM 不用静态ARP掩盖未定位的接收故障
小ping通、大包/RDMA不通 Ethernet MTU、交换机最大帧、RoCE active_mtu与QP MTU 8192、9216、4096不能机械改成相同值
TCP握手卡住 Host服务端是否监听、源路由、防火墙策略、测试端口冲突 不要关闭整个防火墙；按需放行测试路径
TCP握手成功，RDMA卡住 RoCEv2 GID/IP、两端MTU、QP参数、UDP4791路径、版本 TCP通不等于RoCE数据通
单对满速、多对吞吐低 双口共享PCIe、NUMA/内存、竞争、QoS/丢弃/重传 不能直接认定交换机坏或简单相加单口带宽
吞吐骤降，重传增加 沿路错误增量、DSCP分类、PFC与缓冲 仅缩短timeout可能掩盖丢包而未修复原因
改QoS后ARP不通 buffer1/pool是否被驱动重算、是否匹配已知规避条件 只看PFC4配置正确仍可能漏掉普通流量路径
重启后复发 NM、sysctl、hccn.conf、systemd/dispatcher、交换机保存 运行态成功不等于持久化成功
