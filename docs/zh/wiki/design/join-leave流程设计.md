# join-leave流程设计

最近遇到了很多join/leave方面的问题，所以梳理了一下当前develop分支join/leave的流程设计。<br>
我们的系统需要让多个进程（节点）动态地加入或退出一个“组”。为了保证所有存活的节点对“谁在组里”这个问题有完全一致的看法，我们设计了一套基于configStore的同步流程。<br>
整个流程的核心思想是：一次只允许一个节点进行加入或退出操作。这样可以避免多个操作同时发生导致的状态混乱。<br>

## 1、 如何实现“一次只允许一个操作”？

我们通过一个特殊的全局事件记录（在代码中叫 SMEM_GROUP_LISTEN_EVENT_KEY）来协调所有节点。<br>
这个记录也就是SmemGroupInfo，对于join包含两个关键信息：<br>
当前是什么事件（例如：节点5要加入、节点3要退出、或者什么都没有）。<br>
一个版本号（version）。<br>
版本号的规则很简单：<br>
如果版本号是 偶数（0, 2, 4...），就表示当前没有人在操作，组的状态是稳定的。<br>
如果版本号是 奇数（1, 3, 5...），就表示有某个节点正在执行加入或退出操作，大家先别动。<br>

## 2、 当一个节点想加入（Join）时，具体怎么做？

假设 节点A 想加入组，它会按以下步骤操作：<br>
第一步：尝试“宣布”我要加入<br>
节点A先去读取那个groupinfo_。<br>
如果发现里面的版本号是奇数，说明已经有别的节点在操作了。那节点A就什么也不做，等一小会儿再重试。<br>
如果发现版本号是偶数，说明现在是空闲状态。节点A就立刻尝试修改这个记录：<br>
把事件内容改成 “JOIN_EVENT (节点A要加入)”。<br>
把版本号加1（从偶数变成奇数）。<br>
并且，这个修改必须是一个原子操作（代码里用 CAS 实现）。这意味着，如果在节点A读取和修改之间，有别的节点抢先改了，那节点A的这次修改就会失败。<br>
关键点：<br>
只有成功完成这个“读-改-写”原子操作的节点，才算真正获得了“开始操作”的资格。我们可以把它理解为“抢到了操作权”。<br>
第二步：等待所有节点处理<br>
一旦节点A成功“抢到操作权”，它就会停下来等待。<br>
此时，所有其他节点（包括节点A自己）的后台监听线程都会立刻收到通知，知道有新事件了。<br>
它们会各自执行用户定义的 joinCb 回调函数，每个节点更新本地 rankSize 并触发回调segment 的import。rdma 的import的流程<br>
第三步：宣布操作结束<br>
当节点A自己的后台线程也处理完这个加入事件后，它会唤醒正在等待的节点A。<br>
节点A被唤醒后，就知道大家都处理完了。于是它再次修改全局事件记录：<br>
把事件内容清空（设为 NULL_EVENT）。<br>
把版本号再加1（从奇数变回偶数）。<br>
这样，全局状态就恢复到了“稳定”模式，下一个想加入或退出的节点就可以开始尝试了。<br>

## 3、 Leave（退出）流程

Leave 流程和 Join 几乎一模一样，只是把事件类型从 JOIN_EVENT 换成了 LEAVE_EVENT。
核心的“抢操作权 -> 等待处理 -> 宣布结束”三步走逻辑是完全相同的。<br>
