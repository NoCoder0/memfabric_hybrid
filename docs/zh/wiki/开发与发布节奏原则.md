# 开发与发布节奏原则

[TOC]

## 1. 推荐分支职责

### 1.1 分支定义

- `master`
  - 当前最新beta版本。
  - 20260914起，接受PR直接合入。

- `develop`
  - 下一个 minor 版本的集成分支。
  - 所有改动必须通过 PR 和基础 CI 再进入。
  - 20260914起废弃，beta代码直接合入master分支

- `br_feature/*`
  - 新特性、优化、重构分支。
  - 生命周期尽量短，尽快合回 `develop`，在回合完成后删除。

- `release/x.y`
  - 从 `master` 按特性规划切出。
  - 只允许 bugfix、文档、版本号、release note、低风险配置变更，不允许特性合入。
  - 正式版本 tag 只打在这里。

### 1.2 推荐流转

```mermaid
flowchart LR
    F[feature/*] --> D[develop]
    D --> M[master]
    M --> R[release/x.y + tag vX.Y.0]
    H[hotfix/x.y.z] --> R
    H --> D
```

这张图对应两个原则：

- 新特性先进入 `develop`。
- 已发布版本的修复先落稳定分支，再回灌 `develop`。

## 2. 怎么发版本

### 2.1 发版时机

- 大致每 3 个月发布一个大版本（版本号前两位变化）的正式版本，例如 `v1.4.0`。
- 有bug fix修改会触发小版本（版本号第三位变化）迭代发布

## 3. 特性和 bugfix 怎么处理

### 3.1 特性

- 特性必须走 `feature/*`，不要直接堆在 `develop`。
- 大特性必须拆小，避免一个 PR 包太多内容。
- 未完成特性如果要先合回，必须有 feature flag、配置开关或默认关闭路径。
- 到切 `release/X.Y` 的时间点，还没收敛的特性直接顺延到下一个版本。

原则：**未完成特性不应该阻塞发版。**

### 3.2 bugfix

```mermaid
flowchart TD
    A[发现 bug] --> B{是否影响已发布版本}
    B -- 否 --> C[直接修 develop]
    B -- 是 --> D{是否阻塞当前稳定版本}
    D -- 是 --> E[在 release/X.Y 或 hotfix/X.Y.Z 修复]
    D -- 否 --> F[评估是否进入下一个 patch]
    E --> G[cherry-pick -x 回灌 develop]
    F --> G
```

原则：**同一个 bug 只写一次修复逻辑，不做两边各修一遍。**

## 4. 落地的最小改造

建议优先做这几件事：

1. 所有开发都走短生命周期分支，不在 `develop` 上长期堆大改动。
2. 一个 PR 尽量只做一件事，降低审查和回归成本。
3. 大特性用 feature flag 隔离，避免“没做完但挡住发版”。
4. `release/X.Y` 切出后严格冻结，只收 bugfix。
5. 同时维护的稳定分支不要太多，建议最多 1 到 2 条。
6. 给 `develop` 增加基础 CI 和 nightly 回归，尽早发现失稳。

一句话总结：

**不要等稳定了再切 release，而要把“稳定”这件事放到 release 分支的固定窗口内完成。**
