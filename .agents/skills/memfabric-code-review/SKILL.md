# memfabric-code-review — 新增代码监视与审查

## 目标

对**新增或变更的代码**（非全量重构）进行监视/审查，确保所有错误退出路径都包含有意义的错误日志，且日志中包含导致失败的原因以及报错函数/调用点的关键参数。

## 范围限定

- **只关注新增或变更的代码行**，不要求审查整个文件或大范围重构。
- 如果发现已有旧代码也存在同类问题，仅做简要提示（如"旧代码也有类似情况"），不做强制修改。

## 审查要点

### 1. 识别错误退出路径

扫描所有**错误/异常退出**的代码路径，包括但不限于：

- `return error` / `return err`
- `throw` / `throw new Error()`
- `panic` / `recover`
- `os.Exit` / `process.exit`
- 异常分支（`if err != nil` 等）
- 提前 `return` 且返回值为错误/异常
- 断言失败
- 调用外部服务/库后未检查错误

### 2. 检查错误日志要求

每个错误退出路径**必须**满足以下条件：

- **有错误日志记录**（`log.Error`、`logger.Error`、`console.error`、`t.Log` 等）
- **日志内容包含**：
  - 导致失败的原因（原始 error message 或自定义描述）
  - 报错函数/调用点的**关键参数**（见下方定义）
- 日志级别应为 `Error` 或等效级别（不要求用 `Fatal`/`Panic`，除非确实致命）

### 3. 关键参数选择原则

选择要打印的参数时，遵循以下优先顺序：

| 优先级 | 参数类型 | 示例 |
|--------|---------|------|
| 高 | MemFabric 标识符 | `rankId`、`localRank`、`remoteRank`、`deviceId`、`pid`、`threadId`、`channel`、`handle` |
| 高 | 资源名/资源句柄 | `shmName`、`shmKey`、`storeKey`、`bufferId`、`memHandle`、队列名、文件名 |
| 高 | 通信/任务定位信息 | `traceId`、`requestId`、`jobId`、`batchTag`、`opId`、`transferDescNum`（仅在代码中真实存在时） |
| 中 | 路径/端点 | 文件路径、`ASCEND_MF_STORE_URL`、etcd endpoint、TCP/HCOM/RDMA 地址和端口、API endpoint |
| 中 | 配置项 | 超时时间、重试次数、阈值、`worldSize`、`rankSize`、`opType`、`xpu_type`、HCOM/RDMA 开关 |
| 中 | 外部调用目标 | ACL/URMA/HCOM/etcd 接口名、下游服务名、RPC 方法名、`smem_bm_*` / `hybm_*` 调用点 |
| 中 | 状态码/错误码 | `ret`、`errno`、`StoreErrorCode`、`BM_*` 错误码、ACL/HCOM/URMA 错误码、退出码 |
| 低 | 内部中间值 | `idx`、`offset`、`batchSize`、`len`/`length`、`srcVA`/`dstVA`（仅在有助于定位时） |

不要照搬通用业务系统的示例，避免引入本项目不存在的泛业务 ID 概念。若当前模块没有
`traceId`、`requestId`、`jobId` 等字段，不要为了满足模板而虚构字段。

### 4. 敏感信息禁止打印

**禁止打印**（除非确认已脱敏）：

- 证书、私钥、passphrase、token、access key、secret key、API key 等认证材料或密钥内容
- `ASCEND_MF_STORE_URL`、etcd endpoint、TCP/HCOM/RDMA 地址中携带的用户名、密码、token 等认证信息
- 完整环境变量 dump；如需打印，只保留与定位相关且不含认证信息的变量名和值
- SMEM/HYBM buffer、tensor、共享内存、device/host memory 的原始数据内容
- 配置存储中的完整 value；如 value 可能包含密钥、证书、拓扑或节点私有配置，必须脱敏或只打印 key

如需打印上述敏感信息，必须使用 `***` 或 `[redacted]` 脱敏。

### 5. 代码格式与函数规模

审查新增或变更代码时，应检查：

- 单行宽度不超过 120 个字符；超过时应优先通过换行、提取变量或拆分表达式提升可读性。
- 新增函数原则上不超过 50 行；超过时应优先拆分为语义明确的小函数或提取局部辅助逻辑。
- 不为了满足 50 行限制做机械拆分；拆分后的函数边界必须能表达独立意图，不能降低可读性。
- 生成代码、长字符串、表格型数据、宏展开参数等特殊场景可例外，但审查结果中应说明原因。

如发现问题，审查结果中标注为「行宽超限 / 新增函数过长」。

### 6. 环境变量文档同步

审查新增或变更的代码时，如果发现：

- **新增环境变量**：必须检查 `doc/environment_variables.md` 是否已同步添加该变量的说明（名称、用途、默认值等）
- **删除或废弃环境变量**：必须检查 `doc/environment_variables.md` 是否已同步移除或标注废弃

如文档未同步，需在审查结果中明确指出。

### 7. 对外接口文档同步

审查新增或变更的代码时，如果涉及**对外接口**修改：

- **对外接口**包括但不限于：C/C++ 公开头文件/API、Python 绑定/API、公开类/函数/枚举/错误码、参数/返回值/异常/行为语义变化
- **C 接口变更**：重点检查 `doc/API.md` 是否已同步更新；**Python 接口变更**：重点检查 `doc/pythonAPI.md` 是否已同步更新
- **同一能力同时暴露给 C 与 Python**：两个文档都必须检查

如文档未同步，需在审查结果中明确指出。

### 8. UT/test 字面量规范

审查新增或变更的 `test/`、`tests/`、`ut/`、`*_test.cpp`、`*_test.cc`、`*_test.h` 等测试代码时：

- 不要使用难以理解的裸数字字面量；应优先提取为有语义的 `constexpr` / `const` 变量，例如 `kRankSize`、`kBufferSize`、`kTimeoutMs`。
- C/C++ 整数字面量应根据被比较或赋值对象的类型补齐后缀，例如 `1U`、`1UL`、`1ULL`、`1024UL`、`4096ULL`。
- 当字面量用于 `EXPECT_EQ` / `ASSERT_EQ` / mock 期望值时，应避免无后缀的整数字面量导致有符号/无符号或位宽不清晰。
- `0`、`1` 仅在语义非常明显的布尔、空指针、枚举默认值或错误码场景中可以接受；如果代表大小、rank、device id、timeout、count、offset、address 等，应命名或加类型后缀。

如发现问题，审查结果中标注为「测试字面量可读性 / 类型后缀缺失」。

### 9. 例外情况

以下情况可**接受**缺少错误日志，需在审查结果中注明「可接受例外」：

- **上层统一记录**：错误会逐层上抛，由顶层中间件/框架统一记录（需确认上层确实有记录逻辑）
- **测试代码**：测试中的错误路径，使用 `t.Fatal` / `t.Error` 已足够，不强制额外 `t.Log`
- **日志会过载的循环**：高频率循环中每次失败都打日志会导致日志爆炸，可在外层聚合或在循环外记录汇总
- **快速失败辅助函数**：如 `mustXxx` 函数（约定 panic），语义上不要求日志

## 审查输出格式

发现问题时，按以下格式输出建议：

```
### 问题位置
`文件路径:行号`

### 错误路径
描述错误如何发生

### 缺少的信息
- [ ] 错误原因
- [ ] 关键参数（列出具体参数名和值/脱敏值）

### 建议
```代码片段或建议描述```

### 类型
缺失日志 / 参数不足 / 敏感信息泄露 / 行宽超限 / 新增函数过长 / 测试字面量可读性 / 类型后缀缺失（如有）
```

## 原则

- **最小化修改**：只建议补必要的错误日志，不做无关格式化、变量重命名、重构等修改。
- **优先本地定位信息**：优先打印能直接定位到请求/任务/资源的参数，而非泛泛的"something went wrong"。
- **一致性**：建议的日志格式应与项目现有日志风格一致。
